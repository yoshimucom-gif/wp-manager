# CHANGELOG / 引き継ぎメモ — Affiros リライト プラグイン

このファイルは、**別のチャット（セッション）で作業を引き継ぐため**の記録です。
新しいセッションでこのプラグインを触るときは、まず `README.md`（概要・使い方）と
このファイル（ファイル構成・改修履歴・設計判断・既知の制約）を読んでください。

---

## ファイル構成

```
affiros-rewrite/
├── affiros-rewrite.php   … 本体。定数定義・設定取得・メニュー登録・CSS読み込み
├── README.md             … 概要・インストール・設定・使い方
├── CHANGELOG.md          … このファイル（改修履歴・引き継ぎ）
├── admin/
│   ├── rewrite-page.php   … リライト実行画面（投稿一覧＋単記事/一括。JSはインライン）
│   ├── settings-page.php  … 設定画面（APIキー・モデル・リライト既定値）
│   └── ajax-handler.php   … AJAXエンドポイント（fetch_posts / run_single / save）
├── includes/
│   ├── claude-api.php     … Claude API ラッパー（自動リトライ付き）
│   ├── rewrite-engine.php … プロンプト生成・実行・出力パース・安全弁
│   ├── post-fetcher.php   … WP_Query での投稿取得・更新
│   ├── marker-inserter.php… 商品カードマーカー挿入（本体 insert_card_markers 準拠）
│   └── article-type.php   … 記事タイプ判定（本体 infer_title_article_type 準拠）
└── assets/
    └── admin.css         … 管理画面CSS
```

## 設計上の要点

- WP REST API を使わず `WP_Query` / `wp_update_post` で完結 → ホスティングの WAF・海外IP制限による 403 を回避する（これがプラグインの存在理由）。
- Claude APIキーは `wp-config.php` の定数 `AFFIROS_REWRITE_API_KEY` を最優先で使う。定義されていれば管理画面DBより優先され、プラグインの更新・再インストールでも消えない。
- 一括リライトは確認画面を経由せず順次保存する。ただし壊れた内容でライブ記事を上書きしないための安全弁あり（v0.4.0 参照）。
- リライト結果は `wp_update_post` 経由で保存 → WordPress のリビジョンで復元可能（リビジョン無効サイトでは画面に警告を出す）。

## バージョン履歴

### v0.4.39 (2026-06-09)
**新機能: 重複投稿クリーンアップ**
- 背景: Affiros9 本体 v1.7.27 以前で発生していた予約投稿の重複送信バグの結果、
  同じタイトルの記事が WP に複数回投稿されてしまった環境を救済する。
- 追加: 管理メニュー「Affiros リライト → 📦 重複投稿削除」を追加。
  - 「重複スキャン」: 全 post を post_title でグルーピングし、複数あるグループを抽出
  - 各グループ: 最古（最小 ID）の1件を「保持」、残りを「削除候補」として表示
  - 個別削除（行ごとの 🗑 ボタン）または「全重複を削除」で一括削除
  - 既定はゴミ箱送り（wp_trash_post）。チェックで永久削除モード切替可
  - スキャン後にプレビュー → 確認 → 削除、の二段階フロー
- 対象: post タイプのみ。ゴミ箱・自動下書き・inherit ステータスは除外
- 新規ファイル: `admin/duplicate-cleanup-page.php`

### v0.4.38 (2026-06-09)
**本番一括投入前の事故防止 3 点**
1. **画像消失の防止（プレースホルダー方式）**:
   - 症状: プロンプトの「使ってよいタグリスト」に <img> が含まれておらず、Claude が
     リライト時に画像を勝手に落とすケースがあった。
   - 修正: 元記事の `<figure>...</figure>` と裸の `<img>` を `<!--AFFIROS_MEDIA_N-->`
     コメントに置換してから Claude へ送り、応答中のプレースホルダーを元のメディアに
     戻す方式に変更。Claude が出力に含めなかった画像は記事末尾に救済挿入される
     （「画像が全部消えた」事故を物理的に防ぐ）。
   - プロンプト側にも「<figure>/<img>/<a> は src/alt を改変せず原文の位置に保持」
     ルールを明記して二重防御。

2. **「復旧を試みる」誤操作の防止 admin notice**:
   - Affiros リライターの管理画面に「⚠️ 壊れたテーブルブロックが見つかりました
     （直近100件中 N 件）。「復旧を試みる」は絶対に押さないでください」という
     警告バナーを表示。修復ページへのリンクボタン付き。
   - スキャンは直近100件を 1 時間キャッシュ。修復後はキャッシュをクリア。

### v0.4.37 (2026-06-09)
**新機能: 既存記事の壊れた wp:table ブロックを一括修復するページを追加**
- 背景: v0.4.36 で「これから生成する記事」は壊れなくなったが、v0.4.35 以前で
  既にリライト済みの記事は壊れたままで、編集画面を開くと『想定されていない
  コンテンツ』エラー → 「復旧を試みる」でブロックごと消える問題が残っていた。
  リライト済み記事が大量にある場合、1件ずつ手動で修復するのは現実的ではない。
- 追加: 管理メニュー「Affiros リライト → 🔧 テーブル修復」を追加。
  - 「全件スキャン」ボタンで post / publish + draft + future + private の
    全記事を 100 件ずつページングしながらチェック。
  - 壊れた wp:table ブロックを 1 件以上含む記事をリスト表示。
  - 「全件一括修復」または個別記事の修復ボタンで `wp_update_post()` 経由で
    本文を正規化版に置換。リビジョンが自動作成されるので元に戻せる。
- 内部: `Gutenberg::count_malformed_table_blocks()` / `repair_table_blocks()` /
  `normalize_table_for_gutenberg()` を public 化し検出/修復の共通実装に。
  idempotent なので同じ記事に何度実行しても安全。
- 新規ファイル: `admin/table-repair-page.php`

### v0.4.36 (2026-06-09)
**バグ修正: 比較テーブルが Gutenberg バリデーションエラーで消える**
- 症状: リライト後の記事を WP 編集画面で開くと、比較テーブルブロックが
  「このブロックには、想定されていないか無効なコンテンツが含まれています」と
  赤エラー表示。「復旧を試みる」を押すとブロックごと消失し、結果として
  H2 と H2 の間のコンテンツが消えて連続H2状態になる。
- 原因: WP の `wp:table` ブロックは HTML スキーマが厳格で、
  - `<figure class="wp-block-table">` でラップ必須
  - `<tr>` は `<thead>` または `<tbody>` の直下である必要
  - `<table>` / `<td>` 等の inline style / class / border 属性は許容されない
  という条件を満たさないと「想定されてないコンテンツ」と判定される。
  Claude は `<table border="1" style="..."><tr><td>...</td></tr></table>` の
  ような「scheme 不一致な table HTML」を返すことがあり、`gutenberg-converter.php`
  はそれを `<figure>` でラップするだけで内側を正規化していなかった。
- 修正: `Gutenberg::normalize_table_for_gutenberg()` を追加し、`<table>` 出力を
  Gutenberg の table block が受け付ける形に正規化:
  - `<table>` の全属性を剥がして `<table class="">` に統一
  - `<thead>` / `<tbody>` / `<tr>` の属性を全部剥がす
  - `<td>` / `<th>` は `colspan` / `rowspan` / `scope` のみ保持、それ以外は剥がす
  - `<thead>`/`<tbody>` 外の生 `<tr>` を `<tbody>` で自動ラップ
- 効果: リライト後に編集画面を開いてもテーブルブロックが赤エラーにならない。
  「復旧を試みる」を押す必要がなくなり、コンテンツが意図せず消える事故も防ぐ。
- 注意: v0.4.36 より前に作成した壊れたテーブルブロックは、再リライトすると
  正常に置き換わる。

### v0.4.35 (2026-06-09)
**バグ修正: 「元記事が長すぎます」誤判定**
- 症状: 本文 8000 字程度の記事でも「元記事が長すぎます（50432文字 / 上限30000文字）」で
  一括リライトが全件失敗するケースがあった。
- 原因: 長さ判定が「生HTMLのバイト数」を見ていた。記事を装飾している
  `<!-- wp:paragraph -->` などの Gutenberg ブロックコメント、大量の inline style
  付き `<div>`／`<span>` などのマークアップが本文の 5〜6 倍に膨らんで上限を超えていた。
- 修正:
  - `Pre_Cleanup` に Gutenberg ブロックコメント（`<!-- wp:* -->` / `<!-- /wp:* -->`）の
    除去を追加。Claude に渡す入力からも無駄なノイズが消える（プロンプト効率改善）。
  - `Rewrite_Engine` の `MAX_SOURCE_CHARS` 判定を「タグ・コメント除去後の本文文字数」
    で行うように変更。エラーメッセージも「本文 X文字」と明示。
- 効果: 装飾だらけの記事もリライト可能に。本来弾くべき「本文 3万字超」の長文記事は
  これまで通り中断される。

## 既知の制約・今後の検討事項

- **広告挿入定義のカスタム非対応**: 本体の「広告挿入定義」UIでマーカー規則を変更しても、プラグインは本体のJSONを読めないため反映されない。プラグインは `DEFAULT_CARD_INSERTION_PATTERNS` 相当のみ対応。
- **長文記事のタイムアウト**: Claude の応答がホスティング（ConoHa 等）の PHP / プロキシ制限を超えると「通信エラー」で失敗しうる。一括実行では Haiku・少数バッチが安全。
- **元記事の上限**: 30000 字。超える記事はリライトを中断する。
- **画面JS**: `rewrite-page.php` にインライン（約260行）。必要なら `admin.js` へ分離可能。
- **アンインストール**: `uninstall.php` は無し。設定（APIキー等）を意図的にDBへ残す方針のため。
